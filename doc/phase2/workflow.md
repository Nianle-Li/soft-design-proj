# Phase 2 开发流程与门禁

本文件为开发计划，不是已经完成的实现报告。[需求与验收矩阵](requirements.md)标记增量需求；[Phase 1 实验报告](../README.md)及其需求清单保留历史结论。Phase 2 题目约束新增行为，Phase 1 题目继续约束原有功能。已发布 `final` 不移动；只有 Phase 2 交付核验完成后才创建 `p2`。

## 每个切片的工作规则

1. 选择一项可验证能力，核对题目原文、精确输出、失败后状态及 Phase 1 兼容影响；尚未定义的语义先形成 ADR，不把猜测写成事实。
2. 对当前切片的重要设计至少比较两种可行做法。CLI 模块边界、扩展点及依赖检查器的决策属于框架重构阶段，不作为 VSCode 实践的前置条件；进入 CLI 重构时，先确定边界并更新依赖检查器，再新增相应模块。
3. 先建立能公平发现缺陷的测试或会话基线，包含正常、错误、边界和插件禁用路径；再做最小实现，不为通过测试而弱化题目约束。
4. 验证类型、Lint、格式、依赖、追踪范围、相关独立测试和全部 Phase 1 回归；审查差异和运行代码的依赖方向。
5. 每个切片把需要保留的设计判断、注意点、截图来源、人工核对和 AI 建议纠偏简明记录到 [关键证据与设计记录](record.md)，供实验报告复用；不写开发流水账，也不重复已有文档。
6. 每形成可独立验收的能力，及时设计一个内聚的小提交，列出范围、验证结果和建议提交信息供用户审核；得到确认后才提交或推送。

阶段可按依赖调整先后，但不得越过对应的测试和 ADR 门禁。VSCode 与 CLI 是两部分均须完成的交付，不以一方替代另一方。

## 兼容性与装配验证

- 保存 `final` 的 Phase 1 §6 完整会话及其输出作为逐字节基线。新增插件（含树标签）禁用时，同样输入必须得到相同输出；不能只比较退出码或宽松匹配。
- A/B 装配使用同一插件集合、顺序、options、初始 SVG、输入和固定工作目录。`dir` 的输出日志写在工作目录外，避免测试自身改变目录内容。命令输入与预期输出分开保存。
- 各插件独立可测。加载器须覆盖模块缺失、默认导出缺失、清单不符、激活异常、重复注册、非法配置、部分注册回滚和继续加载；属性处理器须覆盖部分修改后失败的原子性。
- 接入新插件的提交检查 `git diff --name-status C^ C`：方式 A 运行代码只新增插件并改一个顶层装配文件；方式 B 已有运行源码不变，仅新增插件和配置。内核及既有插件的差异必须为空；先确认路径真实存在，再排除新增插件目录检查。测试、文档和依赖元数据须逐项说明。
- `docs/metrics/` 的脚本以 Git 中的 `final` 和最终 `p2` 为比较点，按 CLI 内核、装配处、插件拆分文件职责、行数和圈复杂度；VSCode 单列，排除依赖和构建产物。`p2` 未创建前可先验证脚本形式，不伪造最终指标。

## 当前进度与阶段边界

VSCode 扩展实践已有源码、测试、独立宿主截图和 A.3 分析；磁盘内容变更及不完整 XML 的 Outline 界面变化已观察到，编辑器内直接输入后的可见刷新仍待人工复核，程序化宿主测试已覆盖 `WorkspaceEdit` 的文档符号结果。CLI 架构决策与插件实现尚未开始，Phase 1 报告和输出未修改。新的 SVG 示例已在 `.gitignore` 与追踪检查器中按精确路径放行，仓库没有整体放宽 `*.svg` 排除规则。
