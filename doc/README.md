## 6. 测试与质量保证

### 6.1 测试策略

- 每个需求先写测试或 CLI transcript，再实现最小功能。
- 每项功能至少覆盖正常、失败、边界、回归风险；编辑命令另覆盖 execute、undo、redo 和新编辑后的 redo 清空。
- 领域语义、命令历史、CLI 输出、SVG 读写应能独立验证；完整会话用于验证协作关系。
- 修复缺陷必须先用测试稳定复现，防止仅凭人工操作“碰巧修好”。

### 6.2 标准验证命令

```powershell
npm run typecheck
npm run lint
npm run format:check
npm test
npm run coverage
npm run cli
```

`npm run coverage` 与完整命令 transcript 回放属于交付前质量门禁；不将尚未实际执行的结果写为“通过”。

### 6.3 测试记录

## 8. Git 提交约定

提交信息采用 `<type>: <可验证结果>`，其中 `type` 为 `docs`、`test`、`feat`、`fix`、`refactor` 或 `chore`。

建议节奏：先提交需求/架构决策与测试，再提交实现；修复缺陷时先提交复现测试，再提交修复。每次提交前检查工作区，避免纳入 `node_modules`、覆盖率产物和临时 SVG。
